# Supermicro IPMI Client

A remote management client for Supermicro servers whose BMC runs AMI MegaRAC
firmware — a replacement for the JViewer Java applet, which needs the
long-deprecated Java Web Start.

Electron + React + TypeScript, with no native dependencies and no runtime
dependencies at all.

> **Status: 0.x.** The KVM console, power control, IPMI sensors and Virtual
> Media all work against real hardware.

## Features

- **KVM console** — video, keyboard and mouse, with a from-scratch decoder for
  the AVICA2A video codec.
- **On-screen keyboard** — a full layout with a numeric pad, clicked with the
  mouse for keys the host system swallows (F1–F12 on macOS, Alt+Tab and Win+R
  in the window manager). Modifiers latch, so combinations work with one hand
  on the mouse.
- **Power control** — power on, graceful and immediate shutdown, power cycle,
  hard reset. It runs over IPMI over LAN rather than over the console, so it
  keeps working when the KVM session does not — which is the state a server
  usually has to be restarted from.
- **IPMI over LAN** (port 623) — temperature, voltage and fan sensors, chassis
  state, the system event log.
- **Virtual media** — mounting a disk image over the IUSB protocol, either as a
  virtual CD-ROM or as a virtual USB disk. The choice matters: a plain ISO only
  boots as a CD-ROM, while a hybrid image (most Linux installers) boots either
  way — which is the way out when the BMC's cd-media service is broken, as it
  is on some boards.
- **Network discovery** — sweeps an address range for BMCs over UDP 623 and
  offers what answered for adding to the list. The range is prefilled from this
  machine's own network.
- A server list with passwords held in the OS keychain.
- **Advanced settings per server** — timeouts, ports, KVM bandwidth and input
  timings, kept in the profile because they describe the far end rather than
  this machine. Every one of them has a default, and the form resets to them.
- English and Russian interface, following the system language by default.

## Requirements

- A Supermicro server with an AMI MegaRAC BMC (developed against X9/X10-era
  boards that ship JViewer).
- Network access to the BMC web interface (TCP 80/443), the KVM port
  (TCP 7578) and, for sensors and power control, IPMI over LAN (UDP 623).
- Node.js 20 or newer to build from source.

## Running from source

```bash
npm install
npm run dev      # development
npm run build    # build
npm start        # run the built application
```

If Electron did not download during `npm install` — which happens behind
restrictive networks — install the binary by hand:

```bash
curl -L -o electron.zip \
  "https://github.com/electron/electron/releases/download/v$(node -p "require('./node_modules/electron/package.json').version")/electron-v$(node -p "require('./node_modules/electron/package.json').version")-darwin-$(node -p process.arch).zip"
unzip -q electron.zip -d node_modules/electron/dist
echo "Electron.app/Contents/MacOS/Electron" > node_modules/electron/path.txt
```

## Building distributables

```bash
npm run dist          # every platform at once
npm run dist:mac      # macOS: dmg and zip, arm64 + x64
npm run dist:win      # Windows: an NSIS installer and a portable exe, x64
npm run dist:linux    # Linux: AppImage, deb and tar.gz, x64
```

The results land in `release/`. The icon is generated by a script
(`npm run make:icon`), which runs automatically before a build, so no binary
asset lives in the repository.

Everything can be built from macOS, Windows and Linux included: the project has
no native modules, and electron-builder downloads NSIS and AppImage itself.
Code signing is not configured — the builds are unsigned, so the system may ask
for confirmation the first time you run them.

## Checking against a live server

The debug scripts run without a graphical interface. The host is required;
credentials may also come from `BMC_HOST`, `BMC_USER` and `BMC_PASSWORD`, which
keeps the password out of the process list.

```bash
npm run check:auth    -- <host> [user] [pass]   # login, then fetch the kvmtoken
npm run check:kvm     -- <host> [user] [pass]   # a KVM session; frames to .data/samples
npm run check:ipmi    -- <host> [user] [pass]   # sensors, chassis, event log
npm run dump:services -- <host> [user] [pass]   # the BMC service configuration
npm run decode:frame                            # decode captured frames into PNG
npm run e2e           -- <host> [user] [pass]   # end-to-end run of the app
```

`npm run check:vmedia` and `npm run check:hotkey` **reboot the server** — lab
hardware only.

## How it is put together

```
main (Node)                        renderer (React)         worker
───────────                        ────────────────         ──────
bmc/auth      HTTP login, JNLP
kvm/session   TCP 7578, IVTP  ──frame (~20 KB)──▶  KvmConsole ──▶ AVICA2A
kvm/hid       keyboard, mouse                      Toolbar        OffscreenCanvas
ipmi/session  UDP 623, RMCP+  ──▶  SensorPanel
vm/session    TCP 5120, IUSB + a SCSI target over an ISO
```

The compressed frame is passed to the renderer untouched and decoded in a Web
Worker: the finished raster would be sixty times larger.

Sockets and files are reachable only from the main process; the renderer runs
without `nodeIntegration` and talks to the outside world exclusively through
`contextBridge`.

The main process never produces user-facing prose. It emits message keys, and
the renderer translates them, so switching the language retranslates text that
is already on screen. See `src/shared/i18n.ts`.

## Protocols

Everything was reconstructed from a decompiled JViewer. **The decompiled
sources are not part of this repository** — they belong to AMI. What follows
are the details that had to be reproduced, or deliberately worked around:

- **Getting a token.** `GET /Java/jviewer.jnlp?EXTRNIP=<ip>&JNLPSTR=JViewer`.
  Without the `JNLPSTR` parameter the BMC silently returns a JNLP with no
  `kvmtoken` in it.
- **KVM handshake.** The server speaks first with `SESSION_ACCEPTED`; the client
  answers with three packets. In the validation packet the declared length
  (140) does not match the actual one (324 bytes) — that is the original's own
  discrepancy, and it has to be repeated verbatim or authentication fails.
- **The AVICA2A video codec.** A stream of 16-bit tokens, RGB555, two screen
  buffers and a persistent raster. Runs come in two flavours, and the mode is
  chosen by decoder state rather than by the token itself. The raster index is
  computed by the absolute formula `y*resX + (actResX-1-x)`: the original's
  incremental path is only equivalent to it when `actResX == resX`, and on real
  hardware it is not (the test bench reports 738x414 with actResX=800).
- **Keyboard.** Byte 1 of the report, reserved by the USB HID standard, carries
  an auto-release flag here: on `keyup` of an ordinary key no packet is sent at
  all, or characters come out doubled.
- **Service configuration.** A record is 55 bytes with 32-bit ports, not the 51
  bytes with 16-bit ports that the decompiled `ConfPkt.java` describes. The
  virtual media ports are only trustworthy from here: in the JNLP the BMC
  substitutes `0x7FFFFFFE` when a service is unavailable.
- **Virtual media.** The SCSI layer lived inside a native library in the
  original (`libjava{cdrom,harddisk}wrapper`), so the drive emulation is
  written from the SBC-3/MMC-6 specifications. The reply format, which the
  decompiled Java does not show at all — it hands a buffer to the library and
  sends whatever comes back — was read out of that library's `ExecuteSCSICmd`
  and `SetErrorStatus`, and confirmed against a live BMC. A reply is the
  request echoed back with four fields changed:

  | Payload bytes | Meaning |
  | --- | --- |
  | `0..3` | length the BMC expects — echoed untouched |
  | `4..7` | transfer tag — echoed untouched |
  | `9..24` | the CDB |
  | `21..24` | in a reply: error flag, sense key, ASC, ASCQ (over the tail of the CDB) |
  | `25..28` | in a reply: length of the data transferred (u32 LE) |
  | `29..` | the data |

  Getting `25..28` wrong is not a subtle failure: the BMC reads zero bytes
  transferred and retries the same command once a second, forever.

## Limitations

- Input encryption (Blowfish) is not implemented: BMCs do not require it by
  default.
- Only images are redirected, not physical drives in this machine.
- Virtual media is read-only: `WRITE(10)` is refused. Booting an installer
  needs nothing more, and a writable redirect would let the remote server
  modify a file on your disk.
- **A BMC may not release the virtual media slot when a connection drops.** A
  stuck slot shows up in `/rpc/getvmediacfg.asp` as
  `V_ACTIVE_*_SESSIONS == V_MAX_*_SESSIONS`, with the port replaced by
  `4294967294`. Neither `ipmitool mc reset cold` nor restarting the services
  through `/rpc/setvmediacfg.asp` helps; fully removing power does.
- On the test bench the `cd-media` service turned out to have a corrupted
  configuration (`IFCNAME: ''`, port `4294967294`), and the firmware refuses to
  reconfigure it through `/rpc/setservicecfg.asp` (`HAPI_STATUS` 384/387).
  `fd-media` (5122) and `hd-media` (5123) work, which is why the mount menu
  offers "as a USB disk" — a hybrid ISO boots that way just as well. Services
  the BMC reports as unavailable are shown disabled in that menu.

## FAQ

**Which servers does this work with?**
Supermicro boards whose BMC runs AMI MegaRAC and offers JViewer in its web
interface — mostly the X9 and X10 generations. Newer boards with an HTML5
console use a different protocol and are not supported. If the BMC web
interface offers you a `.jnlp` download for the remote console, this client
should speak to it.

**Do I need Java installed?**
No. That is the entire point: the protocols are reimplemented in TypeScript.

**Why does it accept the BMC's self-signed certificate?**
Because a BMC almost always carries a self-signed certificate issued for its
factory hostname, and with verification enabled the connection is simply
impossible. The original JViewer trusts everything too. If you have replaced the
certificate with one from your own CA, set `insecureTls: false` in the session
options and the connection becomes MITM-resistant. BMCs belong on a management
network that is not routed from anywhere else regardless.

**Where are my passwords stored?**
In the OS keychain through Electron's `safeStorage` — Keychain on macOS, DPAPI
on Windows, the Secret Service on Linux. Profiles themselves (address, port,
user name) sit in plain JSON in the application's `userData` directory. If the
system offers no secure storage, passwords are simply not saved: writing them
to disk in the clear is not an option.

**F1–F12 do nothing on macOS. Why?**
The system claims that row for brightness and volume, so the keypress never
reaches the application. Either hold Fn, or open the on-screen keyboard from the
toolbar and click the key there — it goes straight to the BMC and bypasses the
host keyboard entirely.

**Why do modifiers on the on-screen keyboard behave oddly?**
They latch, because a mouse cannot hold Ctrl down and click another key at the
same time. One click arms a modifier for a single key; a second click holds it
until you click it again. "Release all" clears everything.

**The mouse cursor in the guest does not follow mine.**
Switch the mouse mode in the toolbar. Absolute mode works when the guest OS has
the BMC's USB tablet driver; older systems and some BIOS screens need relative
mode.

**Can I have several sessions to one server?**
The BMC limits how many KVM sessions run at once, and this client keeps exactly
one. When the limit is reached the BMC refuses the connection and says so.

**Does it support IPMI serial-over-LAN?**
Not yet. The IPMI session code already speaks RMCP+ with AES-CBC-128, so the
payload type is there; the console side is not written.

**Something does not work with my BMC.**
Run the matching `npm run check:*` script — they print the raw protocol
exchange, which is far more useful in a bug report than a screenshot. Please
include the BMC firmware version from `npm run check:ipmi`.
